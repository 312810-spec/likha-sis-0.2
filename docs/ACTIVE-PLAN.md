# Windows and Android delivery plan

## 1. Android feasibility

Preserve Windows behavior. Add Android key protection through a platform adapter;
prove the existing SQLCipher/Rust storage path on arm64 and a 16 KB environment.
Use the real DB, not an in-memory demo. Force-stop/reboot during and after saves.
Suggested experiment budget: five focused engineering days, not an automatic
deadline or blocker. If critical integration fails, compare a Kotlin companion.

## 2. One complete teacher workflow

Use assigned Grade 10 Math/ICT synthetic classes. Cache rosters, mark attendance,
enter a quiz, recover offline, reconnect to the current school hub, resolve an
intentional concurrent correction, review/export on Windows and restore a backup.
Keep subject and adviser attendance separate. Empty scores are not zero.

## 3. Packaged-device evidence

Test online/offline Windows installation, lower-end Android operation, standard
user permissions, signing/upgrade preservation, accessible controls and portable
recovery. Include schema/sync metadata and accepted operation IDs in backup.
Measure success, speed and lost/duplicate/conflicting operations; no fictional pass.

## 4. Expand from evidence

Reconcile unfinished existing work before merging overlapping changes. Add
school-year lifecycle and validated forms after the core workflow works.
Nutrition, AI, optimized timetables, district reporting and full mobile parity
remain later candidates, not permanent prohibitions. Keep one sync authority;
evaluate hosted authority explicitly rather than silently changing the hub.
