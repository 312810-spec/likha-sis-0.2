# Compounding Engineering Decision Record

Date: 2026-08-25. Evaluates the external-tooling shortlist proposed for
strengthening LIKHA's development system so defects compound into
durable protection rather than repeating. This closes the discovery
phase — per the directing prompt's own instruction, do not continue
searching for more agent frameworks/plugin packs/tooling ecosystems
unless a real capability gap appears, an adopted tool goes stale, or
clear evidence of a substantially better replacement shows up.

## Condensed 20-scenario pass

Full 20-option enumeration would mostly restate the shortlist itself
(most "N only" scenarios score below a combined low-risk-first rollout
on every LIKHA priority — security/correctness → DepEd compliance →
teacher usability → maintainability → zero billing). The scenarios that
actually discriminate:

- **Minimal quality flywheel** (nextest + already-adopted cargo-deny/
  gitleaks + knip) vs. **broad plugin installation** (everything in the
  prompt at once): minimal wins decisively — zero new hooks, zero
  architecture change, measured real benefit, reversible in minutes.
  Broad installation risks exactly the "plugin zoo" the directing
  prompt explicitly warns against, with several items (Beads, Serena,
  Playwright/Tauri-driver UI regression, promptfoo agent regression,
  cargo-mutants) each individually large enough to deserve their own
  focused evaluation, not a bundled rollout.
- **Correctness stack now** (proptest + cargo-mutants) vs. **later,
  domain-targeted**: later wins. Both tools are genuinely valuable but
  need a specific domain target (auth/lockout, grading, migrations) to
  produce real signal rather than generic coverage noise — better spent
  once a concrete invariant is in question than adopted speculatively
  this session.
- **UI-quality stack now** (Impeccable + Playwright/native-driver
  regression) vs. **deferred, single-workflow pilot later**: deferred
  wins for the same reason — the directing prompt's own suggestion
  (start with learner editing, since real defects were just found there)
  is sound, but choosing the _right_ native-Tauri-capable driver
  (Playwright vs. `tauri-driver` vs. WebdriverIO) is itself a real
  research question this session did not have room to do justice to
  alongside everything else in Phase A.
- **Compounding-learning + agent regression** vs. **awesome-llm-apps
  focused skills + existing system**: the latter, narrower, wins — two
  small skills (`scope-drift-review`, `commit-archaeology`) plus one
  learning-registry file cover the durable-lesson concept without
  standing up a second planning/evaluation system alongside the ADRs/
  memory/handoff LIKHA already has.

**Recommended**: minimal quality flywheel (Phase A, executed this
session) + a documented, honest deferral of Phases B-H with clear
resumption criteria, rather than a rushed partial attempt at all of
them.

**Next best**: Phase A + a Phase B proptest pilot scoped to
`repository::user`'s lockout logic specifically (the newest, most
security-relevant invariant in the codebase) — deferred this session
for time, not rejected; a strong candidate for the very next available
slot.

## A real bug the verification pass itself caught

Running `npm run quality` as part of this session's own verification
surfaced 3 genuine TS test failures — `AttendanceScreen.test.tsx` and
`MonthlySummaryScreen.test.tsx` inject a fixed clock into
`AttendanceApplicationService` but not into the screen component itself,
which reads the real system clock for the date picker's default. The
session's real date advanced past the tests' hardcoded date while this
task was in progress, exposing the drift. Diagnosed, fixed (froze
`Date` via `vi.useFakeTimers`/`vi.setSystemTime` in both files'
`beforeEach`, restored via `afterEach`), verified green, and recorded as
a durable lesson: `docs/learning/ERROR-PATTERNS.md`'s "Tests that inject
a fixed clock into the service but not the component" entry. This is
exactly Loop D (weak test → stronger invariant → future regression
caught) from the directing prompt, produced by simply running real
verification rather than assuming a previously-green suite stayed
green.
