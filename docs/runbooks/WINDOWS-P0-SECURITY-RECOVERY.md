# Windows P0 Security and Recovery Verification

## Purpose

This checkpoint produces release evidence for the Windows package, SQLCipher
database, DPAPI key storage, installer lifecycle, accessibility, and recovery
behavior. It closes verification debt; it does not authorize real learner PII.

Use synthetic names and values only. Run destructive scenarios only inside a
disposable Windows account or VM with no real LIKHA database.

## Gate A — automated, non-destructive

From a clean repository checkout on the Windows target machine:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\verify-windows-p0.ps1
```

The script records the exact Git commit, runs the Grade 12 migration and
transition computation checks, SQLCipher/DPAPI tests, canonical quality and
security gates, Playwright/axe smoke gate, and the native Tauri build. It also
captures BitLocker, firewall, Secure Boot, and Windows Update posture without
recording the computer or user name.

The default evidence directory is under `%TEMP%`. Review every file before
sharing it. A PASS requires every result in `manifest.json` to be `PASS`; an
unavailable security scanner or skipped build is not a release pass.

## Gate B — packaged application lifecycle

Use the installer generated by Gate A on a disposable Windows profile.

1. Record installer filename and SHA-256 with `Get-FileHash`.
2. Install without administrator elevation if the selected package supports it.
3. Launch and create only the documented synthetic school, accounts, learner,
   enrollment, attendance, and grade records.
4. Close and reopen the application; confirm all records persist.
5. Install the same version again; confirm it does not erase or duplicate data.
6. Upgrade from the immediately previous signed test build; confirm migration
   30 applies once and the Grade 12 policy list contains five legacy groups.
7. Uninstall. Record whether application data remains, matching the documented
   product policy. Reinstall and confirm retained data opens successfully.

Do not mark this gate passed from `cargo test` or browser UI tests alone.

## Gate C — copied-database resistance

With LIKHA fully closed:

1. Locate the Tauri app-data directory for identifier `org.likhasis.app`.
2. Copy `likha-sis.db`, `likha-sis.key`, and any `-wal`/`-shm` sidecars to a
   disposable test folder. Never use a production or personal cloud folder.
3. Search the copied bytes for the distinctive synthetic markers. Record that
   no marker is found.
4. Open the copied database using ordinary `sqlite3` without a key. Record the
   expected `file is not a database` failure.
5. Sign into a different disposable Windows account and attempt to use the
   copied `.key`. Record that DPAPI unprotect fails closed and that no database
   content is exposed.

Do not upload database or key files as evidence. Store only commands, sanitized
terminal results, checksums, and the witnessed PASS/FAIL record.

## Gate D — backup and witnessed restore

The present DPAPI design supports same-machine/same-Windows-profile restore. It
does not support recovery on another device or after loss of the Windows DPAPI
profile. The drill must prove both behaviors honestly.

1. Use a disposable synthetic-data profile and close LIKHA completely.
2. Copy the complete app-data directory to two encrypted test destinations.
3. Record SHA-256 hashes of the source and both copies.
4. Move the original app-data directory aside; do not permanently delete it.
5. Restore copy A to the same profile and launch LIKHA. Verify every synthetic
   record and migration version.
6. On a different disposable Windows account or VM, restore copy B. Confirm it
   fails closed because DPAPI cannot unwrap the originating profile's key.
7. Return the original directory to its original location after the test.
8. Have the ICT custodian and one witness sign the result and record date,
   commit, installer hash, machine class, and failures. Do not record passwords,
   keys, database files, real names, or learner information.

A cross-device failure is the expected result today, but it remains a release
risk requiring an approved recovery design. It must not be relabeled as a pass.

## Gate E — native accessibility

Run the packaged binary, not the Vite browser preview.

- Complete login, navigation, attendance, class record, learner enrollment,
  export, error recovery, and logout using keyboard only.
- Repeat representative workflows at 200% Windows text scaling.
- Test with Narrator and NVDA separately.
- Confirm the skip link, focus order, drawer trap/return, table headers,
  validation messages, offline state, and Efficient/Comfortable/Guided controls.
- Record defects by workflow, screen-reader, severity, and reproduction steps.

## Release decision

The learner-PII gate remains **BLOCKED** until Gates A–E pass, the recovery risk
has an approved treatment, and the school head/authorized data-protection
authority signs the production-data decision. A partial run is evidence, not
release approval.
