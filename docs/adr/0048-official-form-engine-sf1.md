# ADR-0048: Authoritative-Template Official-Form Engine (SF1)

Status: Accepted
Date: 2026-08-26

Work classification: `DEPED_OFFICIAL_FORM + NATIVE_EXPORT + COMPLIANCE_SENSITIVE`.

## Context

Wave 2G ended with a verified, green checkpoint (`c23cf16`). This wave's
brief directs building the first reusable pattern for taking trusted
LIKHA local data and filling an authoritative DepEd spreadsheet
template while preserving the template itself — not merely "export
Excel." SF1 is the concrete first form; the pattern must generalize to
SF9/SF10/etc. later without rediscovery.

The brief names a specific architectural preference to treat as the
working hypothesis unless the repository holds stronger current
evidence: `Tauri -> scoped local sidecar -> Java -> Apache POI/HSSF ->
official .xls template`. No such decision exists anywhere in this
repository already (checked: no prior ADR, `PROJECT-MEMORY.md`, or
`ACTIVE-PLAN.md` entry mentions Java, POI, HSSF, or a sidecar runtime) —
so this wave evaluates it as a candidate on equal footing with the
others, per the brief's own instruction to run the full ten-scenario
process when no durable accepted decision already exists.

## Authoritative-template evidence gate

Searched the repository for any existing official SF1 (or related
School Form) template: `find`/`grep` across the whole tree for
`*sf1*`, `*.xls*`, "Apache POI", "HSSF", "sidecar". Result: **no
authoritative SF1 template exists anywhere in this repository.** The
only SF1-related files are `src-tauri/tests/fixtures/sf1_synthetic_*.xls`
— synthetic, clearly-labeled fixtures used for the _import_ direction
(reading a teacher-provided enrollment workbook), generated by this
project's own `generate_sf1_fixtures.py`, not an official blank SF1
export template. ADR-0043 already disclosed this same gap for the
import side ("No official DepEd SF1 `.xls` template exists anywhere in
this repository").

**Consequence, per the brief's own §2 instruction**: this wave does not
fabricate a template and does not claim official SF1 fidelity. The form
engine is built and tested against an explicitly synthetic template
fixture (see "Template registry" below). **Official SF1 fidelity
against a real authoritative DepEd template remains `NOT_VERIFIED`** —
recorded as verification debt with the exact missing artifact named,
not silently treated as passing.

One piece of real, repo-owned evidence about DepEd's _current
distribution format_ does exist, though, and it materially affects the
runtime decision below: ADR-0009 (`docs/adr/0009-sf2-export-and-official-form-engine.md`)
and `docs/product/M8-DECISION.md`'s "Update 2" record that this project
was given a real, in-use, current (school year 2025) DepEd workbook —
`CONSO SF v2025.xlsx` — and inspected its structure directly. It is an
**`.xlsx` (OOXML) workbook, not legacy `.xls` (BIFF)**. This is the
single strongest piece of format evidence this project has ever
obtained about a real DepEd School Form (SF2, from the same
DepEd Order No. 4 s. 2014 "modified School Forms" family SF1 belongs
to), and it was already sitting in this repository, unconsulted, before
this wave's research began.

## Ten-scenario decision

Evaluated against LIKHA's priorities plus the brief's own rubric
(fidelity, offline correctness, zero billing, packaging/reliability,
maintainability, security surface, implementation complexity,
reversibility):

1. **Java + Apache POI/HSSF sidecar** (the brief's named working
   hypothesis) — real strength: POI has both HSSF (`.xls`) and XSSF
   (`.xlsx`) with the ecosystem's most complete fidelity story for
   preserving merged cells/styles/formulas on write. Real cost: a JVM
   runtime this project has never shipped, a packaging story (jlink/
   jpackage minimal runtime, bundled with the Tauri installer), a new
   sidecar IPC protocol, a new Tauri shell-execution capability, and an
   entirely new process-invocation security surface (§8's threat model)
   — paid in full up front, for a fidelity benefit that stays
   `NOT_VERIFIED` this wave regardless of runtime, since no authoritative
   template exists to be faithful to.
2. **Rust-native spreadsheet library, template-copy + constrained cell
   patching** — `umya-spreadsheet` (MIT, pure Rust, v3.1.0, 1M+ total
   downloads, last published 2026-08-17 — actively maintained) can open
   an existing `.xlsx` file and modify specific cells while leaving the
   rest of the workbook object model intact. Zero new runtime, zero
   packaging story, zero process-invocation surface — the generator is
   just more Rust in the same binary. Real limitation: `.xlsx`/`.xlsm`
   only, no legacy `.xls` (BIFF) support at all.
3. **Direct binary-template manipulation** (hand-rolled OOXML/ZIP-part
   patching without a spreadsheet library) — rejected: reinventing a
   large, error-prone parser/serializer for a format `umya-spreadsheet`
   already implements correctly is pure risk with no benefit over
   option 2.
4. **LibreOffice/headless automation** (`soffice --headless` macro/UNO
   scripting) — rejected: introduces a large, non-trivial-to-package
   external application dependency (worse than the JVM sidecar's
   footprint), a scripting-injection surface, and unpredictable
   behavior differences across LibreOffice versions; no evidence this
   project needs LibreOffice-specific fidelity umya-spreadsheet lacks.
5. **Template-copy + constrained cell patching as its own named
   pattern** — this is the _shape_ both option 1 and option 2 use; not
   a separate runtime choice, folded into the recommendation.
6. **Provider-independent sidecar abstraction (build the port first,
   defer the runtime choice)** — the port (`OfficialFormGenerator`,
   §4) is built regardless of which option below is chosen; not a
   competing option, a shared requirement.
7. **Minimal/no-new-runtime approach: CSV output, same as ADR-0009's
   SF2 export** — rejected specifically for this wave: the brief
   explicitly requires preserving an authoritative template's actual
   binary/structural fidelity (merged cells, formulas, layout), which a
   CSV re-derivation cannot do by definition. Reusing ADR-0009's
   `FieldDisclosure`/`sanitize_filename_component` patterns where they
   apply is still correct; abandoning template fidelity as this wave's
   goal is not.
8. **Windows-only native engine with a portable-application port
   deferred** — this project already targets Windows-first with a
   documented `windows-future` gating pattern (ADR-0040); both option 1
   and option 2 are compatible with that existing convention, so this
   isn't a separate axis, it's inherited from the existing target
   strategy either way.
9. **Hybrid: Rust-native now, Java/POI held as the documented Next
   Best with an explicit switch condition** — this is how the
   recommendation below is actually structured; see below.
10. **Unconventional: do nothing this wave beyond the reusable port and
    a fully synthetic proof-of-concept, explicitly deferring any real
    runtime commitment until an authoritative template is obtained** —
    considered and rejected as too conservative: the brief asks for a
    working, tested vertical slice, not merely an interface; a
    synthetic-fixture-backed real implementation is achievable this
    wave without waiting on template acquisition, per §2's own
    guidance ("You may still build the reusable engine against an
    explicitly synthetic template fixture").

**Recommended: option 2 — `umya-spreadsheet`, pure Rust, no new
runtime.** This is a deliberate departure from the brief's named
working-hypothesis preference (option 1), made on the strength of
evidence the brief itself permits ("do not overturn it without
stronger current evidence"): this repository's own real,
already-obtained DepEd workbook (`CONSO SF v2025.xlsx`) is `.xlsx`, not
legacy `.xls` — the one fact that would have forced POI's HSSF path is
absent, and the fact that IS present favors the option with zero new
runtime, packaging, or process-invocation surface. Every fidelity
guarantee this wave can actually demonstrate (§6) is demonstrated
identically well by either runtime, since both are working against the
same synthetic fixture; the runtime choice does not change what's
provable this wave, only the cost of achieving it.

**Next Best: option 1 — Java + Apache POI/HSSF sidecar**, retained as
the documented runner-up, not discarded. **Switch condition** (explicit,
checkable, not vague): switch to this if either becomes true —
(a) an authoritative SF1 template is obtained and it turns out to be
legacy `.xls` (BIFF), which `umya-spreadsheet` cannot open at all; or
(b) fidelity verification (see "Fidelity guarantees" below, once run
against a real authoritative template) shows `umya-spreadsheet`
unacceptably dropping styles, merged regions, or formulas that the real
template requires to be preserved byte-for-byte or structurally
equivalent. The `OfficialFormGenerator` port (see "Architecture
implemented" below) is designed specifically so this switch is an
adapter replacement for `formgen::umya_adapter`, not a rewrite of
`formgen::sf1`/`commands::formgen` — independent architecture review
confirmed this holds for the port itself, with one exception recorded
below (`formgen::fidelity` is umya-typed and would need rewriting, not
reuse, if this switch is ever made — see "Independent review findings
and fixes").

## Architecture implemented

```text
commands::formgen          (Tauri command / application-service role —
                             reads authorized data via repositories,
                             builds a domain request, resolves the
                             output path, invokes the port below; the
                             only module that touches a `tauri::AppHandle`
                             or reads the bundled template resource)
        |
formgen::OfficialFormGenerator   (port trait — provider-agnostic)
        |
formgen::umya_adapter      (infrastructure adapter — the only PRODUCTION
                             module that imports `umya_spreadsheet`)
        |
Trusted bundled template (`resources/sf1/`, verified by
formgen::template before any parsing is attempted)
```

`formgen::sf1` (the domain contract — `Sf1GenerationRequest`/
`Sf1LearnerRow`/`Sf1GenerationResult`) uses only `serde`/`String`/
`Option`/`Vec` — confirmed by independent architecture review to contain
no `umya_spreadsheet`, `tauri`, or `rusqlite` type anywhere.

`formgen::fidelity` (the structural-fidelity comparator, described under
"Fidelity guarantees" below) is `#[cfg(test)]`-only, not part of the
production build — independent review found an earlier version of this
module was an unconditional `pub mod`, while this module's own doc
comment already claimed `umya_adapter` was "the only module that
imports `umya_spreadsheet`," which was false as long as `fidelity` was
unconditionally compiled in. Gating it to test-only both matches its
only actual caller (a test in `umya_adapter.rs`) and makes that claim
true again for the production binary.

## Template registry / versioning

`formgen::template::TemplateDescriptor` is this wave's template-identity
concept: `form_type`, `version` (`"synthetic-v1"` — see the Fidelity
Disclosure above for why no real DepEd version identifier exists yet),
`expected_sha256` (pins the exact trusted bytes), `data_sheet_name`,
`other_expected_sheet_names`, `first_data_row`, `max_learner_rows`,
`data_columns`, `header_cells`. `formgen::template::verify_identity`
hashes the supplied bytes and rejects any mismatch with a generic error
BEFORE any attempt to parse them as a spreadsheet — confirmed by
independent security review to run as the literal first statement in
`generate_sf1`, with the bundled resource's actual SHA-256
independently recomputed and confirmed to match the pinned constant.
`formgen::umya_adapter::verify_structure` is a second, defense-in-depth
layer (checked after the hash passes and the workbook parses): every
expected sheet name must actually be present.

Independent architecture review found `TemplateDescriptor`'s shape is
reasonably generic in principle, but `data_columns: [u32; 4]` and
`header_cells: [(u32, u32); 4]` are fixed-size arrays hardcoded to SF1's
specific 4-column/4-header-cell layout, and `Sf1GenerationRequest`/
`OfficialFormGenerator::generate_sf1`'s name and signature are SF1-named
and SF1-shaped. **This wave's own reusability claim is corrected here**:
`TemplateDescriptor`'s general shape and the port/adapter separation are
reusable in spirit for a future SF9/SF10; the domain contract
(`formgen::sf1`), the port method name, and the adapter's cell-writing
loop are not — a second form would need its own request/row types and
its own generation method (or a second trait), not merely a new
`TemplateDescriptor` constant. Recorded as verification debt below
rather than over-generalized speculatively this wave, per the brief's
own anti-premature-abstraction instruction.

## Data mapping

`commands::formgen::generate_sf1_form` reads `school::find_by_id`,
`section::find_by_id_in_school`, and
`section_membership::roster_for_section` (all pre-existing, already
school-scoped repository functions — no new query logic), maps each
`SectionRosterMember` to an `Sf1LearnerRow`, and writes: LRN (blank if
absent), family name, given name, sex (blank if absent) per learner row;
school name, school year, grade level, section name in the four header
cells. No field is fabricated or zero-filled for a gap in the data
model — every populated cell traces to a real column already captured
elsewhere in this schema, matching ADR-0009's `FieldDisclosure`
discipline in spirit (a full `FieldDisclosure` struct was not built
this wave, since SF1's generation surface has no comparably large set of
DepEd-form fields this schema doesn't capture at all — unlike SF2's
attendance-statistics gap).

## Fidelity guarantees

`formgen::fidelity::SheetFidelitySnapshot`/`compare` prove STRUCTURAL
fidelity (not byte-for-byte, which `umya-spreadsheet` cannot guarantee
across a save regardless of what changed — internal metadata like
calc-chain caches gets rewritten every time): sheet name, visibility
state, merge ranges, row heights, column widths, formulas outside the
generator's own write region, and defined names (where a sheet's print
area lives).

**What independent review found and what was fixed**: the comparator's
own doc comment claimed defined-names/print-area coverage before that
field/check actually existed in the struct — fixed, `defined_names` is
now a real field, captured and compared. Sheet-protection comparison
checks only _presence_, not the protection object's contents (a
password could be silently dropped while the sheet still reads as
"protected") — disclosed as a limitation in the module's own doc
comment, not fixed this wave. The `excluded_write_region` parameter
supports only one rectangular exclusion box; against this wave's own
fixture that box is slightly wider than the true write surface (it also
excludes the never-written row-8 column-header-label cells), which is
harmless here but would hide a fidelity break in a real template with a
formula in that over-excluded area — disclosed in both the module doc
comment and the specific test that uses it.

Empirically verified this wave (synthetic fixture only — see the
Fidelity Disclosure section for why "official SF1 fidelity" itself
remains a separate, unresolved claim): the SF1 sheet's merges/formulas/
sizing/defined-names survive generation with 10 learners written;
the untouched "Notes" sheet (including its own sheet-protection
password) survives unchanged; sheet order/count/names survive; the
footer `=COUNTA(A9:A38)` formula survives generation at the full
30-learner capacity, one row before it.

## Security and privacy

Full threat model, per independent security review (no blocking
findings; three should-fix items, all addressed below):

- **Malicious output path / path traversal / overwriting arbitrary
  files** — closed by construction: `commands::formgen::generate_sf1_form`
  accepts NO output-path parameter from the caller at all. It derives
  the path itself from session-authorized school/section data run
  through `export::sanitize_filename_component` (reused from ADR-0009,
  not re-derived). Independent security review verified this actually
  closes the threat: `sanitize_filename_component` strips `/` and `\`
  (both in its reserved-character denylist), so a `..` sequence
  embedded in a section name can never function as a path-traversal
  component — it survives only as inert literal text inside one
  filename, since the separator character that would make it dangerous
  is itself stripped.
- **Overwriting the source template** — the generator never opens the
  template path for writing; it parses bytes handed to it, writes only
  to a caller-resolved output path, and an independent test
  (`the_source_template_file_is_never_modified_by_generation`) re-reads
  the actual on-disk template file before/after generation and asserts
  byte-equality.
- **Untrusted/corrupt/tampered template** — `verify_identity` (SHA-256
  hash pin) rejects any non-exact-match before parsing; `verify_structure`
  is a second, independently-testable layer (see "Template registry")
  confirming expected sheets are present even after a hash match.
- **Shell/process/injection surface** — none exists. Confirmed by grep:
  zero occurrences of `Command::new`/`std::process::Command` anywhere in
  `formgen::*`/`commands::formgen`. The Java/POI sidecar architecture
  named as this wave's initial working hypothesis was not adopted in
  code, consistent with the ten-scenario decision above.
- **Malformed workbook / oversized input** — a post-hash-check parse
  failure is caught and converted to a fixed, generic error (never the
  underlying `umya-spreadsheet` error text — see below); the learner
  count is checked against `max_learner_rows` before any cell is
  touched; the generation request itself is built server-side from the
  school's real enrollment, never deserialized from an untrusted IPC
  payload (the Tauri command only accepts `section_id`/`as_of_date`
  strings).
- **Partial/crashed generation & temp-file leakage** — atomic write via
  a sibling `.tmp` file, `sync_all()`, then rename; **independent
  security review found a real gap here**: an earlier version of this
  code cleaned up the temp file on a write failure but not on a rename
  failure, since the rename call sat outside the cleanup closure —
  **fixed**, the rename is now inside the same closure, so any failure
  (write or rename) triggers cleanup. A genuine panic mid-write (not a
  returned `Err`) is a disclosed, accepted residual limitation — see
  `sibling_temp_path`'s doc comment — rather than wrapped in
  `catch_unwind`, per the reviewer's own offered resolution.
- **Unauthorized generation across schools** — `section_id` is
  caller-supplied the same legitimate way `export_section_monthly_sf2`
  already accepts one; isolation holds because
  `section::find_by_id_in_school` resolves to `None` for a foreign
  section, and the command returns `Ok(None)` rather than generating
  anything. Verified by `tests/formgen.rs`'s
  `generating_for_another_schools_section_returns_none_not_an_error`.
- **Learner PII exposure — generated files are NOT encrypted (new
  disclosure, an independent-security-review finding)**: unlike the
  SQLCipher-encrypted working database (ADR-0003), the generated `.xlsx`
  is written in plaintext to `<Documents>/LIKHA-SIS/`, an ordinary
  unencrypted user folder — the same characteristic ADR-0009's SF2
  export already has, but neither ADR disclosed it as a deliberate
  data-exposure boundary until now. **This is an intentional, accepted
  design point, now explicitly disclosed**: official-form exports are a
  separate data-exposure boundary from the encrypted working database,
  by design, because a generated form is meant to be printed/submitted/
  shared as a physical or ordinary digital document — encrypting it
  would defeat that purpose. Teachers/registrars should be aware
  generated forms are readable by anything with filesystem access to
  their Documents folder.
- **Authorization gate consistency (new disclosure, an independent-
  security-review finding)**: `generate_sf1_form` gates on
  `sessions.require_active_school_scope` only, no `Capability` check —
  consistent with every other roster/PII-bearing export command
  (`export_section_monthly_sf2`, `export_report_card`,
  `export_learner_roster`, all identical gate), so this is existing
  convention, not a new regression. However, the read-only SF1 _import
  preview_ (which writes nothing to disk) requires
  `Capability::ManageLearners`, while SF1 _generation_ (which writes a
  persistent, unencrypted, PII-bearing file) requires no capability at
  all — an asymmetry worth a conscious decision. **Decision recorded
  here**: keep the existing export-family convention for this wave
  (any active in-school session may generate/export), rather than
  introducing an inconsistency between this command and its siblings —
  revisit uniformly across the whole export family (SF1/SF2/report
  card/roster) in a future milestone if DepEd compliance requirements
  are found to demand it, rather than fixing only this one command.
- **Logs exposing learner values** — the only two `log::warn!` calls in
  this feature log the underlying `umya-spreadsheet` error text only
  (never a learner field), and `AppError::FormGeneration`'s `Serialize`
  impl emits a fixed category string (`"form_generation_error"`) across
  the Tauri IPC boundary — confirmed directly by independent review
  against `error.rs`'s existing test
  (`serialization_never_leaks_underlying_error_detail`).

## Windows packaging spike

`tauri.conf.json`'s `bundle.resources: ["resources/sf1/*"]` plus
`src-tauri/resources/sf1/sf1_template_synthetic.xlsx` (present on disk,

`commands::formgen.rs`'s `app.path().resolve("resources/sf1/sf1_template_synthetic.xlsx",
BaseDirectory::Resource)` is the documented resolution call for it.

**Explicitly `NOT_VERIFIED`**: no `tauri build` installer was produced
or run in this sandboxed development environment this wave — the
actual installed/packaged-Windows-installer resource-resolution path
(as opposed to the dev-mode/source-tree path) has not been proven to
work. The byte-identity test above is a substitute proof that the
_config_ points at the _right file_, not that Tauri's packaged resource
resolution actually finds it post-install. This gap was not disclosed
anywhere in this repository until independent review caught it — now
recorded here and in `docs/VERIFICATION-DEBT.md`.

## Independent review findings and fixes

Three reviews were dispatched per the brief's roles (Form Fidelity/
Correctness, Security/Native Boundary, Architecture/Maintainability).
All three hit this project's recurring reviewer-retrieval bug on the
standard notification channel (a stub confirmation instead of the
actual findings text) and were recovered via the established raw-
transcript-then-retry protocol. **No blocking findings from any of the
three.** Findings and fixes not already covered in the sections above:

- **Test-name-vs-actual-behavior** (Form Fidelity review, the most
  substantial finding set): `rejects_a_structurally_wrong_workbook_even_if_it_were_hash_matched`
  was misleadingly named — its own inline comment admitted it was
  actually caught by the hash check, not the structural check it
  claimed to prove, leaving `verify_structure` genuinely untested.
  **Fixed**: extracted `verify_structure` into its own function with
  three direct unit tests, and renamed the original test to describe
  what it actually proves. `empty_optional_fields_are_written_as_blank_not_a_placeholder_string`
  claimed to distinguish a blank cell from a placeholder empty string,
  but `sheet.value()` reads `""` either way — the test could not
  actually prove that distinction. **Fixed**: renamed to
  `a_missing_optional_field_reads_back_as_an_empty_string_cell`, which
  only claims what's actually true. `a_failed_generation_never_leaves_a_temp_file_behind`
  only exercised the pre-temp-file-creation rejection path (identity
  verification), never the cleanup-on-error branch inside the write/
  rename closure itself. **Fixed**: added
  `a_rename_failure_after_a_successful_write_still_cleans_up_the_temp_file`,
  which is also what surfaced the real rename-cleanup gap fixed above.
  `a_section_with_no_enrolled_learners_generates_a_form_with_zero_rows`
  (in `tests/formgen.rs`) only checked a return-value struct field, never
  opened the generated workbook. **Fixed**: renamed and rewritten to
  actually read the file and confirm the first data row is empty. Only
  two of four header cells (B3/B6) were ever asserted by any test,
  leaving a B4/B5 transposition undetected. **Fixed**: all four header
  cells, plus a second learner row, are now asserted. No test wrote the
  full 30-row capacity to empirically confirm the footer formula
  survives at the boundary. **Fixed**: added
  `writing_the_full_learner_capacity_leaves_the_footer_formula_untouched`.
- **Dead code** (Form Fidelity review): an unused `write_region`
  variable left over from an earlier version of the fidelity test's
  region logic. **Fixed**: removed.
- **Bogus internal ADR citations** (both Architecture and Form Fidelity
  reviews, independently): two source comments cited "ADR-0048 §8" and
  "ADR-0048's disclosed packaging-spike limitation," but this document
  had no numbered sections and no packaging-spike content at the time —
  a documentation-integrity gap the reviewers correctly flagged as
  serious, since production code was relying on claims that didn't
  actually exist in this file. **Fixed**: the citations were corrected
  to name actual section headers, and the "Windows packaging spike" and
  full "Security and privacy" sections that those comments were
  pointing at were written into this document (above) rather than left
  as dangling references.
- **Missing `docs/VERIFICATION-DEBT.md` entry** (Form Fidelity review):
  no entry existed for this wave at the time of review. **Fixed**: see
  `docs/VERIFICATION-DEBT.md`'s Wave 3 entry, added alongside this
  ADR's completion.

## Remaining verification debt

- **Official SF1 fidelity against a real authoritative DepEd template
  remains `NOT_VERIFIED`** — no such template exists anywhere in this
  repository or was obtainable from this environment (see "Fidelity
  disclosure"). This is this wave's single most important open item.
- **Windows packaged-installer resource resolution is `NOT_VERIFIED`**
  — see "Windows packaging spike" above; no `tauri build` installer was
  produced/run in this sandboxed environment.
- **`GeoLevel`-class real-data risk does not apply here** (that was a
  Wave 2G PSGC concern), but the analogous risk exists for SF1: if a
  real authoritative template ever has a different sheet/column/header
  layout than this wave's synthetic fixture, `TemplateDescriptor`'s
  fixed-size `data_columns`/`header_cells` arrays would need to change,
  not just a new constant — not a defect, a scope boundary to remember
  when a real template arrives.
- **Genuine SF9/SF10 reuse requires new code, not just a new
  `TemplateDescriptor`** — see "Template registry / versioning" above;
  the domain contract and port method are SF1-specific. Recorded so a
  future SF9/SF10 milestone doesn't assume more reuse than actually
  exists.
- **`formgen::fidelity` would need rewriting, not reuse, if this
  project ever switches to the Java/POI Next Best** — it is typed
  directly against `umya_spreadsheet::Worksheet`; a POI-backed adapter
  would need to re-parse output bytes independently (umya-spreadsheet
  could still be used purely as a read-only verification tool
  regardless of which library wrote the file) rather than handing an
  umya `Worksheet` object to the existing comparator.
- **Sheet-protection comparison is presence-only, not content-aware**;
  **the fidelity exclusion region supports only one rectangle, and
  currently over-excludes slightly against this wave's own fixture** —
  both disclosed in `formgen::fidelity`'s own doc comment; neither
  fixed this wave (low severity against the current synthetic fixture).
- **A genuine panic mid-write (not a returned `Err`) can still leave a
  `.tmp` file behind** — disclosed in `sibling_temp_path`'s doc comment;
  accepted rather than wrapped in `catch_unwind`, per independent
  security review's own offered resolution.
- **Authorization-gate consistency across the whole export family**
  (SF1/SF2/report card/roster all use session-only, no capability) is a
  deliberate, disclosed decision this wave, not a defect — revisit
  uniformly in a future milestone if DepEd compliance requirements are
  found to demand a capability gate.
