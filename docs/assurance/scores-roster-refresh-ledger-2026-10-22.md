## Source identity and smallest mechanism

ClassRecordJourneyScreen resolves current teaching assignment, school year, grading period and weighting policy, then opens the canonical class record. The workspace is keyed by teacher/assignment/class-record ID. Category and max score come from that record's assessment items. The existing item/application/native boundaries own authority and validation; this change does not add periods, categories, grading rules or migrations. No fresh native/assignment-device claim.

The incumbent itemsReady boolean combined current-source identity with temporary write readiness. Post-authoring refresh changed it false/true, unmounting the score area and re-running the roster effect, clearing rows/errors/grades and changing the generation used by in-flight score replies. Four focused failures reproduced this behavior.

Retain only the same roster contract: current item source + canonical class/item/category/max, with learner-score service in effect dependencies. A transient item check does not change that contract. Different item/service/class, removed item, failed/unconfirmed source and changed max/category still invalidate/reload it. Rename alone does not. Every new score write still checks itemsReady; no queue or automatic replay is introduced. Inputs remain editable memory drafts.

Assessment changes invalidate derived grades separately using a grade-context generation. Old grade reads and bulk-finally callbacks cannot repopulate/clear a newer context. Acknowledged scores increment their item's local revision. If an older item-list snapshot returns after that acknowledgment, keep that item's newer known local recorded/eligible progress instead of overwriting it with the older snapshot. No cross-device merge/persistence claim.
