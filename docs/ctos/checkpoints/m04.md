## Outcome

M04's outcome — "the teacher understands the day and opens the next meaningful task
immediately" — is met for seven of its eight verification items, with the eighth
recorded as out of this milestone's reach by design rather than as an apparent gap.

Like M02, part of this milestone was verification rather than building: three items
(no classes today, unfinished attendance, returned review) already had real
implementation and tests, and needed naming rather than construction. Unlike M02,
three items needed genuine implementation, and the investigation turned up a real
staleness bug in the view that the item list does not name.

The Today surface is split across three screens, which is worth recording because it
shaped every decision: `HomeScreen` is a role router, `MyDayScreen` is the
schedule-backed Today view under the "daily-planner" tab, and `TodaysClassesScreen`
is a second, independent schedule reader. Only `MyDayScreen` reads schedule data.
This milestone's work is entirely in `MyDayScreen` and its read model.

## The three items that needed building

**1. The next class was never computed.** The read model sorted today's classes by
start time and the screen listed all of them; nothing compared against the current
time, so "next" was whatever happened to be first. A teacher at 13:00 with a 08:00
and a 14:00 class would have been pointed at the morning.

`MyDaySummary.next` is now derived in Rust, after the sort it depends on — the first
sorted item whose `starts_at` is at or after the current time, or `None` once the day
has started. Deriving it next to the sort rather than in the UI keeps one source of
truth; the domain type already commits to mirroring the Rust struct exactly, so this
belonged on both sides of the boundary. A "Next up" marker on the schedule entry
makes it the obvious one action.

`now_time` is caller-supplied, matching the wall-clock convention the command layer
already documents and extends: it selects nothing but which of today's classes counts
as next, so a tampered value cannot reach another teacher's data.

**2. Two different empty days read identically.** `schedule_meetings` for an
assignment with no meetings, and for a day nothing meets on, both produced an empty
`schedule` and the sentence "No classes scheduled for you today." A teacher assigned
to classes that have never been given a slot — the actual "no schedule" case — could
not be distinguished from a teacher whose classes simply do not meet today.

`has_any_assignments` now separates them, and the copy differs accordingly. This was
the data that made the item list's "no schedule" real rather than a restatement of
"no classes today".

**6. There was no "pending assignment" concept at all.** `TeachingAssignment` has no
status field, and searching the domains for pending/awaiting states returns only
attendance, conflict, and score-sync states — none of which is a pending assignment.

The honest reading available in this data model: an assignment with no
`schedule_meetings` on any weekday. It is a real next action ("this class needs a
schedule"), it is already distinguishable by the absence of meeting rows, and it adds
no table and no status column — which matters because the read model's own docstring
commits it to computing every field from data that already exists rather than
inventing a task concept. It surfaces in the attention rail with its reason and
**no action button**: there is no scheduling screen to send the teacher to, so none
is offered. Scheduling is M09's scope, and faking a destination would be worse than
none.

## The bug the item list does not name

`ClassWorkspaceScreen` renders _inside_ `MyDayScreen` rather than on its own tab, and
`MyDayScreen` fetched the summary once on mount. Nothing unmounted when a teacher
opened a class, recorded attendance, and came back — so the "Needs your attention"
rail still showed the class they had just dealt with. The mount-time fetch was never
going to be enough.

`onBackToToday` now re-fetches too. This is the same reasoning
`ClassRecordsScreen.handleBackToList` already records — returning from a workspace
must reflect work done inside it, or the screen "looks current but isn't". The tab
switch _between_ screens already remounted and reloaded, so the gap was specifically
the in-place workspace.

## Items verified as already in place

- **no classes today** — filtered by weekday in Rust, empty state on the screen, and
  already tested on both sides.
- **unfinished attendance** — the strongest-covered item: four Rust tests pin the
  exact semantics (pending when no session, or a session with zero entries; cleared
  by one entry or an explicit `NoClass`, because a deliberate decision is not
  pending).
- **returned review** — read as the sync-conflict review queue: a hub-rejected edit
  returned to the teacher who made it, narrowed to that teacher's own conflicts. A
  `MyDayPendingConflict` carries only `id` and `entityKind`; the review screen holds
  the detail, and Today only counts and links.

## The one item this milestone cannot close

**stale offline schedule.** `schedule_meetings` is absent from the sync allowlist
(`EntityKind` lists twelve kinds; `ScheduleMeeting` is not among them), so meeting
rows are local to the device and have no freshness column. A stale schedule has no
transport to arrive through.

What M04 does guarantee, and what it deliberately does not:

- The summary is computed fresh on every call, and the screen reloads on every tab
  return. The view never claims to be current when it is not.
- **No freshness timestamp is shown, because none exists to show honestly.**
  `SyncStatus.lastPullAt` is device-wide and belongs to M13.

**Label: `Unknown`, recorded in `today-cases.md`.** CTOS scopes the sync transport to
M13 and schedule publication to M09; building either here would be M13's machinery
landed early, and asserting a freshness property this codebase cannot demonstrate
would be exactly the unverified-evidence claim the program forbids. The gap is stated
rather than papered over.

## The read path is still duplicated

Worth recording because it is the clearest remaining risk and M04 did not touch it:
`TodaysClassesScreen` re-implements the join `my_day` computes in Rust, and
additionally reads session status that `MyDaySummary` does not. The two screens can
disagree about the same day, and there are three separate "what day is it"
implementations (`MyDayScreen`, `TodaysClassesScreen`, `TeacherWorkspaceScreen`).
Merged into one read path, this is a real simplification; left alone, it is a seam
where a fourth copy can appear. Not fixed here — it predates this milestone, touches
a screen M04 does not own, and is a design decision rather than a defect.
