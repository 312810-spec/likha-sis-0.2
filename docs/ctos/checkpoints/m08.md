## Why the scope is what it is

CTOS.md §M08's contract is one sentence plus a loop:

> The system identifies actionable unfinished work and connects learning evidence
> to intervention/follow-up.
>
> Evidence → identified need → goal → intervention → participation → follow-up →
> outcome.

Reading that against the repository rather than designing blind: the **evidence**
end already existed (class occurrences, attendance, scores — M06/M07), and the
**follow-up** end already existed (`learner_followup_markers`, migration 44, M06).
The genuine gap was the loop's **middle** — the teacher's explicit plan, the
learner's participation, and the outcome — plus the fact that two of CTOS.md §6.1's
actionable items were never surfaced anywhere.

So M08 does two things, and each is one property:

1. **The loop's middle**, as a persisted case anchored to the occurrence and the
   enrollment. Anchoring it to an occurrence (NOT NULL) is what lets
   `authorize_own_assignment` — the same ownership rule that already protects
   follow-up markers — protect cases too, and re-derive ownership on every
   transition rather than trusting a client-supplied case id.
2. **The two §6.1 items that were invisible**: `pendingScoring` ("unfinished
   assessment work") and `pendingFollowups` ("learner follow-up due where
   appropriate"). Both are derived, never stored — the class record already carries
   the completion counts, the markers already exist. This adds no table and no
   status column, which is what `my_day.rs`'s own docstring commits to.

Deliberately out of scope: any AI suggestion or summarization. CTOS.md §M08 allows
"AI can suggest or summarize"; M08 implements only the teacher-confirmed half. The
one place a draft appears is the marker's reason pre-filling the need field — the
teacher's own earlier text, not generated content.

## The change

**1. The learning-support case** (`learner_support_cases`, migration 45). The
state-machine spine is in the schema, not the query, following `OccurrenceStatus`'s
M06 precedent:

```sql
CHECK (participation IS NULL OR status <> 'open'),
CHECK (outcome IS NULL OR status = 'resolved'),
CHECK (resolved_at IS NULL OR status = 'resolved')
```

That is what makes the one-order rule (open → in_progress → resolved) the
database's rather than whichever query happens to be writing. Every write path
returns the case re-read through the joined `CASE_SELECT`, so the learner's name is
always present and never client-supplied.

Two load-bearing details, each named by a test:

- **The id tie-break on listing.** `ORDER BY opened_at DESC, id DESC`. Two cases
  opened in the same millisecond share `opened_at`, which made the original
  `ORDER BY opened_at DESC` nondeterministic and flipped a test. UUIDv7's leading
  bytes are the generating timestamp, so `id DESC` stays newest-first.
- **The marker is cleared after the plan is written, in that order.** The screen
  calls `openCase` then `clearFollowup`, so a failed clear can never lose the plan
  it was raised for. The marker is cleared, never deleted — M06's rule — so the
  occurrence's own history keeps it answerable.

**2. Two new My Day attention lists.** `pendingScoring` iterates the teacher's
assignments and their class records, pushing when `item_count > 0 && recorded_count
< item_count * total_eligible`. `pendingFollowups` is one JOIN across markers →
occurrences → assignments → subjects/sections → memberships → learners, scoped in
SQL. Both are added to the read model the screen already reloads on every return,
so a marker cleared in the support screen disappears from the rail when the teacher
goes back.

One field was added to an existing struct for this: `MyDayPendingFollowup.section_membership_id`.
It is the key `openCase` needs — the case is keyed on the enrollment span, not a
bare learner id — and without it the rail's "Plan support" action could not open a
case on the right learner.

## Two defects found and fixed while building

1. **`ORDER BY` nondeterminism.** The first version of `list_for_occurrence`
   ordered by `opened_at DESC` alone. Two cases inserted in the same millisecond
   share that timestamp, so the "most recent plan first" test could pass or fail
   depending on insertion order. Fixed with the `id DESC` tie-break and documented
   in the function's own doc comment so the reason is not lost.
2. **`getByText` matching text split across elements.** The marker's reason renders
   both in the drafting hint and in the prefilled textarea, so
   `getByText(/Left the exit slip blank/)` found two elements and failed. The test
   now asserts on the textarea's own content (via typing into it) rather than on a
   shared substring. This is the same trap M06 and M07 both hit; it is recorded in
   memory.

## The required loop, and where each step is met

Full case detail with every test name is in `docs/ctos/evals/attention-cases.md`.

1. **Evidence** — already held (M06/M07: the class occurrence, attendance, scores).
   The case is anchored to it, which is what makes the ownership rule apply.
2. **Identified need** — **new**. `need`, required, schema-enforced non-empty, and
   drafted from the marker's reason rather than invented.
3. **Goal** — **new**. `goal`, required; a need with no goal cannot be closed by
   anything the teacher does.
4. **Intervention** — **new**. `intervention`, required.
5. **Participation** — **new**. `participation`, `null` while `open`, recorded by
   one explicit button that refuses to write anything until it is pressed.
6. **Follow-up** — already held (M06's `LearnerFollowupMarker`). M08's addition is
   that it now _reaches_ the plan: `pendingFollowups` surfaces it, and the plan
   clears it once written.
7. **Outcome** — **new**. `outcome`, `null` until resolved, immutable afterward,
   with `resolved_at` recorded as a historical fact CTOS §5 forbids reinterpreting.

- **The browser axe gate does not traverse the new screen.** `npm run quality:ui`
  drives the synthetic dev preview, which renders `AssignedClassFolio` for the
  "Classes" tab rather than the real `MyDayScreen` and seeds no class occurrences
  or follow-up markers, so the new screen has no fixture path to be reached
  through. The screen's own `has no new accessibility violations` test axe-checks
  it in jsdom — structure and ARIA only, explicitly not contrast or layout, since
  jsdom has no layout engine. Both runners ran; neither is claimed for the other.
- **The marker↔case link is a handoff, not a stored foreign key.** A support case
  does not record which marker answered it. The screen clears the marker after the
  plan is written; the case is anchored to the occurrence and the enrollment, which
  is what the ownership rule needs. A "this case closed that marker" query would
  need a new column and is not claimed.
- **No suggestion or summarization AI.** CTOS.md §M08 permits it; M08 implements
  only the teacher-confirmed half. The single draft is the marker's reason
  pre-filling the need field — the teacher's own earlier text.
- **No native Windows or Android evidence this milestone.** The Rust suite
  exercises the new migration and repository against the encrypted device
  database; the installed packages were not built or exercised. Native claims
  remain where M03 left them.
- **`schedule-cases.md`, `reporting-cases.md`, `recovery-cases.md` and
