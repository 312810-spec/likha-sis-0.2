## The change

`ClassroomModeScreen` — the teaching cockpit CTOS.md §6.3 describes. It is reached
from the class workspace's new Classroom row, which hands off only the teaching
assignment id; App keys the cockpit by that id and clears the handoff on return, so
the cockpit unmounts when the teacher goes back to the class and My Day's mount-time
fetch runs fresh.

The cockpit holds: the status chip and the plan the occurrence was started against;
the actual slot, learning target, quick evidence and notes, saved by a debounced
capture; the attendance state with a route into Subject Attendance when it is not yet
settled; the follow-up panel over today's roster; and the occurrence history with
every prior status distinguishable.

Four properties of that design are load-bearing and each is named by a test:

1. **A save in flight does not reschedule itself.** The debounce effect depends on
   `occurrence`, which a successful save updates — so the guard has to compare the
   draft against what was actually persisted, field by field, on normalized slot
   values. An object-identity comparison is always false and loops forever.
2. **A blank slot is `null`, not an empty slot.** A `type="time"` input cleared to
   `""` and sent as `Some("")` is a deviation from the plan, so clearing a mistyped
   slot would flip the class to `changed` instead of back to `planned`. Blank is now
   sent as `null`, which reads as "not recorded".
3. **A throw cannot escape the load path.** Resolving the roster or the marker list
   after the first `await` is inside one `try/catch/finally`; a failure there had
   produced an unhandled rejection and left the screen stuck on "Loading…".
4. **A stale request cannot write into a cockpit that has moved on.** Every
   `setState` after the first `await` is behind a request-id guard, so a teacher who
   starts a class, goes back and opens a different one does not receive the first
   class's occurrence into the second cockpit.

## The four states, and why they stay distinguishable

The status is a stored enum with a schema `CHECK` constraint admitting exactly the
four values — it is not derived at read time from whether fields happen to be filled
in. Three rules keep them from collapsing:

- **The plan is snapshotted at start time**, not joined live. A schedule edited next
  week does not rewrite what this class was planned as, so "changed" keeps meaning
  "changed against what it was planned as".
- **Each transition is explicit and refused in the wrong direction.** `finish` is
  refused while attendance is unsettled; `cancel` requires a non-empty reason and is
  refused against a delivered class; `start` returns `AlreadyOpen`, `AlreadyDelivered`
  or `AlreadyCancelled` rather than silently re-creating the row.
- **A delivered class is not editable from the cockpit.** Reopen is the deliberate
  way back in, and it bumps `revision` and clears the summary so the prior summary
  does not stand as the record of the reopened session.

Cancellation carrying a reason is CTOS.md §5's requirement, not a convenience: advisory
and weather information does not automatically cancel class, so a cancellation is
always a human decision and is recorded as one.

## Command construction

`npm run quality` and `cargo clippy` were both run outside a `| grep` pipeline this
time, and their exit statuses were read directly (`${PIPESTATUS[0]}` and the logged
`CLIPPY_EXIT`). M04's `format:check` false-negative and M05's re-occurrence were both
caused by reading a pipeline's exit status instead of the tool's; the pattern is
recorded in memory and is now applied to every gate.

## Not claimed

- **No native Windows or Android evidence this milestone.** M06 is an
  application/UI-layer change; native claims remain where M03 left them. Migration
  0043 was exercised by the Rust suite against the encrypted device database, but the
  installed Windows package was not built or exercised here.
- **The debounce interval is a chosen latency, not a measured one.** The verified
  property is that a save does not reschedule itself; 500 ms is not claimed as
  optimal.
- **Offline interruption of a capture save is not a case in this registry.** The
  command is synchronous against the device database and the screen surfaces the
  outcome, but a mid-sync-conflict capture interaction belongs to the recovery
  registry, which is still `planned`.
- **`schedule-cases.md` and `reporting-cases.md` remain `planned`** and were not
  promoted by this milestone; M06 did not touch the solver or the reporting snapshot.
- **The duplicated schedule read path is still untouched** — carried forward from
  M04 and M05; out of M06's scope.
- The occurrence stack is claimed as **verified here, not built here**. The Rust
  repository, commands, migration and TypeScript stack were already present and
