## What the surveys found (why the scope is what it is)

Three read-only investigations ran before any edit. Against CTOS.md §M07's
verify list, ten of thirteen items were already implemented and are recorded
below as re-verified rather than rebuilt. Three were partial:

1. **Keyboard attendance.** `AttendanceScreen` marks with `P`/`A`/`T` plus
   ↑/↓ (`handleRosterKeyDown`). `SubjectAttendanceScreen` — the surface
   Classroom Mode routes into when attendance is unsettled — had ↑/↓ only, no
   letter shortcuts. Neither advanced focus after a mark, so a keyboard
   session cost two keystrokes per learner.
2. **Keyboard score entry.** `ClassRecordWorkspace` handled Enter, ↑, ↓ and
   Escape, but not Tab: native Tab left the score grid and moved to the row's
   Excused/N/A buttons instead of the next learner's score.
3. **Correction history.** The append-only `learner_score_corrections` table
   (migration 42), the Rust `correction_history`, the Tauri command, the
   port, the service method and the Tauri adapter all existed. Nothing called
   the service method outside tests — no teacher could see a lineage.

Deliberately out of scope: the class-record "mark reviewed / issue" state
machine. That is the issued-snapshot lifecycle `grading-cases.md` assigns to
M11; building it here would be building M11 early. M07's "review readiness"
is the advisory surface that already exists (`ComputedTermGrade.complete`,
the "N of M recorded" readout, the provisional marker).

## The change

Three surfaces were changed, and each change is one interaction property.

**1. Keyboard attendance, both rosters.** `SubjectAttendanceScreen` gained the
letter shortcuts `P`/`A`/`L`/`E` it did not have — the surface Classroom Mode
routes into when attendance is unsettled. Both screens now advance focus after a
successful mark, which is what turns a roster from two keystrokes per learner into
one. The advance is driven by the repository's success signal: `handleMark` now
returns `Promise<boolean>` and the key handler moves focus only when it resolves
true, so a failed save leaves the teacher on the row that needs them. A letter
typed with Cmd/Ctrl/Alt held is passed through, so browser shortcuts still work
while focus is in the grid.

**2. Tab in the score grid.** `ClassRecordWorkspace` handled Enter, ↑, ↓ and
Escape, but native Tab left the grid for the row's Excused/N/A buttons. Tab now
commits the draft and moves to the next learner, Shift+Tab moves back up, on the
reason input as well as the score input. Same success-conditional rule: a rejected
save does not move focus away.

**3. The correction lineage became visible.** `learner_score_corrections` (migration 42) and the whole read stack up to the Tauri command existed since M01, but nothing
called `correctionHistory` outside tests — a teacher could correct a score and give a
reason, then had no way to see any of it back. `ScoreCorrectionHistory` is that
surface, wired into the class record workspace below the sync evidence for any row
that has a recorded status.

Two properties of that surface are load-bearing and each is named by a test:

- **The fetch happens on expand, not on render.** A class of forty learners with
  collapsed history panels pays zero correction queries. Keyed by saved-row
  identity by the owner, so a new correction remounts the panel and the lineage it
  shows is never stale — the same pattern `ScoreSyncEvidence` uses.
- **Both authors are resolved at the repository, not the client.** `correction_history`
  now LEFT JOINs `users` twice and returns `previousRecordedByName` /
  `correctedByName`, following the `audit_log.actor_username` precedent. The display
  name is never client-supplied. The fields are `Option<String>` for parity with that
  precedent, though the schema's non-cascading `REFERENCES users(id)` means `None` is
  not a state this database can actually reach — proved by a test below.

## Two defects found and fixed while building

1. **`setState` directly in an effect body.** The first version of
   `ScoreCorrectionHistory` called `setLoading(true)` and `setError(null)`
   synchronously in the effect, which `react-hooks/set-state-in-effect` correctly
   rejects. The reset now happens in the toggle handler — which is also the more
   honest place for it, since that is the moment the teacher asked for the panel and
   the "Loading…" feedback should be immediate rather than after the first await.
2. **`getByText` cannot match text spanning elements.** The change line renders
   `15 → <strong>19</strong>` as separate text nodes, so a plain string matcher can
   never match it. Four tests failed on this before the `changeLineText()` helper
   read the paragraph's own `textContent`. The same trap was hit at M06 and is now
   recorded in memory.

## Not claimed

- **No native Windows or Android evidence this milestone.** M07 is an
  application/UI-layer change; native claims remain where M03 left them. The
  correction-history join and its schema guard are exercised by the Rust suite
  against the encrypted device database, but the installed Windows package was not
  built or exercised here.
- **"Fast" is not a measured latency claim.** The verified property is interaction
  shape — one keystroke per learner, no per-row fetch, no modal between entries —
  not a milliseconds figure. No benchmark was run and none is claimed.
- **The class record's `markFinal` state machine is out of scope**, per
  `grading-cases.md`'s assignment of the issued-snapshot lifecycle to M11.
- **`golden-path.md` is still listed as `partial` in the registry and was not
  promoted this milestone.** The registry row predates the file; resolving the
  mismatch is a registry task, not an M07 acceptance item.
