**Recorded:** 2026-10-06
**Branch:** ctos/integration
**Parent commit:** 152de21 (state update after the M04 tag)
**Status:** PASS

## Outcome

"One persistent authorized class context supports the majority of teacher work" is
met, and the acceptance clause is provably met by an App-level test.

M05 turned out to be shaped like M02 and M04: mostly verification. The Class Folio
redesign (PR #102, ADR-0072/0073) had already built the persistent class index, the
opaque worksheet, keyboard-operable tabs, role-adaptive navigation, and the
revalidation on every class-context use. Five of the six required properties already
held and are now named with real tests. **One did not, and it is the one the
acceptance clause names.**

### The clause, and what it implied

> The teacher should not repeatedly reselect grade/section/subject/term when the
> active class already determines them.

Grade, section and subject were already determined — the class context carries
`teachingAssignmentId` as its one canonical identifier, and every consumer
revalidates it against the teacher's current authorized assignments before using its
section/subject ids. **Term was not determined.** `ClassRecordJourneyScreen.resolve()`
blanked the grading period and the DepEd weighting on every mount, and the Class
Folio remounts whenever the teacher moves between Dashboard, My Classes and Class
Record — the folio is keyed by the active destination so the worksheet tab can take
effect. Choose a term, open the record, check another destination, come back: the
same two questions were asked again.

So M05's real work was one piece of session state and the revalidation around it.

## The change

The chosen grading period and weighting are now held in App session state, keyed by
the teaching assignment, and recalled on the next visit. `ClassRecordJourneyScreen`
gains `initialGradingPeriodId` / `initialWeightPolicyId` / `onRecordSelection`;
`resolve()` seeds the selects from those ids once the authoritative lists have
loaded, instead of blanking them.

Three properties of that design are load-bearing and were each given a test:

1. **Recall is not guessing.** The journey's docstring already committed LIKHA to
   never inferring either academic choice from array order, a default flag, or a
   subject name. Recalling a human's own explicit earlier choice is a different
   act, but the distinction only holds because of (2).
2. **The recalled ids are revalidated, and a mismatch falls back to asking.** A
   grading period the school no longer publishes is dropped back to an empty choice
   rather than clamped onto whichever period happens to be first. This is the
   property that keeps the recall from silently meaning a different term — a real
   academic-integrity risk, since scores recorded under the wrong term are not a
   display bug.
3. **The pair is reported only after validation**, so the app can never remember an
   id that was not confirmed to exist in the school's current lists.

The class _record id_ is deliberately still re-derived on every visit from the
validated pair, never recalled. A deleted record is therefore never silently
restored, and a found match reopens rather than creating a duplicate — which is why
"Open class record" is one click after a remount instead of zero. State retention
stops at the term, which is everything the clause asked for.

Cleared with the **session**, not with the class context: `clearSessionWorkContexts`
clears it, `clearClassWorkContext` does not. Going back to Today and reopening the
same class should not re-ask an answered question; leaving the app entirely should.
Same narrowly-typed `useState` handoff pattern as the other App-held ids — still not
a router, URL, global store, or `localStorage`, so ADR-0060's "not persisted" rule is
unchanged.

## The five properties verified as already in place

- **unmistakable identity** — the folio heading names the section, the sheet shows
  subject and school year, an `aria-live` region announces the selection, and the
  class workspace keeps subject, section and schedule visible.
- **keyboard-first desktop flow** — the worksheet tablist uses a roving `tabIndex`
  with Arrow/Home/End, and the Scores pane stays mounted-and-hidden so a score draft
  survives tab switches.
- **touch-safe narrow flow** — phone navigation is Today / Classes / Forms /
  Account, the class index is a list rather than a dropdown, and the browser smoke
  asserts no horizontal overflow at 390 and 320 px.
- **authorized command/search routing** — see below.
- **progressive disclosure** — Overview is the default pane, Scores and Forms are
  reached from it, and the Scores pane's heavier mount happens on first visit only.

### On "command/search routing"

Recorded because the required list names "search" and this codebase has no global
search. The only search inputs are local in-table filters on `SectionRosterScreen`
and `LearnerListScreen`, which filter data already loaded for an authorized section
or school. There is no search surface whose results could cross a tenant or
authorization boundary, so the item reduces to **command routing** — which is
genuinely tested: the assignment is revalidated before its section/subject ids are
used, a stale context cannot retain an actionable class sheet, attendance and class
record open for the selected assignment only, and the contextual return is offered
only when the preserved context actually matches. The label `High confidence`, not
`Verified`, applies to the search half of the item specifically, because the absence
of a global search is a conclusion drawn from sweeping the UI, not a property a test
demonstrates.

## Correction to the M04 checkpoint

`format:check` was **not** actually clean at the `ctos-m04-complete` tag. Two M04
case files (`docs/ctos/evals/README.md`, `docs/ctos/evals/today-cases.md`) failed
Prettier — a markdown table whose columns were not re-padded after the
`today-cases.md` row was added, and `*emphasis*` that Prettier writes as
`_emphasis_`. M04's checkpoint table records all five gates passing, which was wrong
for that one gate.

The M04 code, test, and lint gates were real and are unaffected; 1,331 Rust tests and
1,257 frontend tests did pass. But the program forbids unverified evidence claims, and
this was one, so it is corrected here rather than left standing. Both files are
formatted in this commit and `format:check` now passes across the repo. The cause was
running `npm run quality` through a `| grep` pipeline whose exit status was `tail`'s,
which is exactly how the same failure was masked during M04 — recorded in the M04
checkpoint's own terms as a command-construction error, and now fully resolved.

## Not claimed

- **No class record id is recalled**, by the reasoning above. "Open class record"
  remains one click after a remount.
- **Nothing is persisted to disk or localStorage**, by ADR-0060. Retention is
  session-scoped, exactly as before.
- **The duplicated schedule read path is still untouched** — M04 recorded it;
  `TodaysClassesScreen` still re-implements the join `my_day` computes, and the
  "what day is it" implementations remain three. Out of M05's scope.
- **No native Windows or Android evidence this milestone.** M05 is a state-retention
  change in the web layer; native claims remain where M03 left them.
- The five verified properties are claimed as **verified, not as M05 output** — they
  come from the PR #102 redesign and were re-run here, not built here.
- **The search half of "command/search routing" is `High confidence`, not
  `Verified`**, for the reason given above.
