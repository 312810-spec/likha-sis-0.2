## The one real defect — account switch left a zombie session

`auth::login` called `sessions.set()` to replace the in-memory session but never
revoked the prior row in the persisted `sessions` table. An account switch
therefore left the superseded session live for up to `SESSION_DURATION` (8 hours).

The in-memory `SessionManager` holds exactly one session, so the zombie could not
be used through the normal command path — but `require_active_school_scope` was
specifically written to treat the persisted table as ground truth, independent of
the in-memory copy, precisely so that "a future revocation path that forgets to
do that still cannot leave a revoked session usable." Leaving un-revoked rows
behind on the one path that _changes_ who is authenticated undercut that design.

Fixed at `src-tauri/src/auth/mod.rs` `login`: it now revokes the session it
supersedes before setting the new one. Idempotent, and a no-op on a first login.

Two tests pin it, and the second is the one that makes the fix safe:
`an_account_switch_revokes_the_session_it_supersedes`, and
`a_failed_switch_attempt_leaves_the_existing_session_live` — the revocation must
be a consequence of a _successful_ login, not of the attempt, or a wrong password
at the switch prompt would sign the already-authenticated teacher out.

## Items that needed proving, not building

**Handover of pending work.** No feature was built, because none was needed.
`learner_scores` and attendance are keyed to the assessment item / class record /
section, not to the teacher; `recorded_by_user_id` is provenance, not ownership.
Reassigning a teacher cannot orphan the section's recorded work — the incoming
teacher sees it because they now own the assignment. What _did_ need proving is
that the reassignment also revokes the departing teacher's **write** capability,
and it does: `replace_teacher` deletes the old assignment row, so the old id
simply stops resolving and `authorize_own_assignment` fails closed on it.

**Offline last-confirmed assignment.** `authorize_own_assignment` reads the
_local_ `teaching_assignments` table, which is itself sync-populated, so offline
authorization falls back to the last state this device confirmed. A hub-side
revocation arrives as a delete, `delete_from_sync` applies it, and the next
authorization fails closed. Proved by a new test rather than assumed.

**Sync queue scope.** A deliberate decision, recorded in the eval file so it is
not mistaken for an oversight: the queue is keyed on school, not on the actor who
enqueued. A removed member's already-recorded attendance and scores are legitimate
records of that school's learners, so their queued rows **must** still reach the
hub — dropping them would destroy real teacher work. What removal blocks is _new_
writes, and that guard is one layer up in session revocation. `actor_user_id` is
provenance, never a read filter.

## Items with no new code, because coverage already existed

- **spoofed ID** — the strongest-covered item; eleven representative tests cited
  in the eval file, including enumeration-safety cases that return one generic
  failure so an attacker cannot probe which of several reasons applied
- **revocation** — sessions, memberships, roles, device credentials, and the
  last-School-Head guard
- **adviser vs subject scope** — two separate tables and two separate
  capabilities; the schema explicitly refuses a fake "Advisory" pseudo-subject
  and refuses a mutable `sections.adviser_user_id` column that would silently
  lose prior-year advisers
- **reassignment** — including `replace_teacher` returning the old assignment so
  its deletion can propagate over sync
- **stale async response** — per-screen `requestRef` guards are already tested on
  five screens

## One item recorded as covered by construction, not by a new test

No new test ties a stale async response to an _account switch_ specifically. The
property holds structurally rather than by guard: on session expiry,
`App.tsx` `handleSessionExpired` clears the work contexts and sets the session to
null, which unmounts the entire authenticated subtree — a late response then has
no live component to write into. The per-screen `requestRef` guards cover moving
between contexts _within_ a session. A cross-session test would mostly be testing
React's unmount semantics. This is stated in `access-cases.md` rather than left
as an apparent gap.
