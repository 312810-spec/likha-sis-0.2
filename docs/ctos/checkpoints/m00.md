### Toolchain defects found and repaired at M00

These blocked the baseline and were fixed, not worked around:

1. **`typescript-compiler` missing from `node_modules`.** `npm run typecheck`
   failed with `Cannot find module`. Fixed by `npm install`.
2. **rustc 1.98 vs `rust-version = "1.99"`.** Fixed by `rustup update stable`.
   The update repeatedly failed on `rust-src` with
   `detected conflict: lib\rustlib\src\rust\library\...` because a prior build
   had vendored dependencies *into the toolchain's own rust-src tree*
   (`.cargo/config.toml`, `Cargo.lock`, `Cargo.toml` with
   `replace-with = "vendored-sources"`). Resolved by removing the `rust-src`
   component entirely — it is not required for `cargo test` — after which the
   update completed cleanly.
3. **openssl-src picked the wrong Perl.** `cargo test` failed configuring
   OpenSSL from source because Git's MSYS2 perl (`/usr/bin/perl`) shadowed
   Strawberry Perl and lacks `Locale::Maketext::Simple`. Strawberry Perl
   (`C:\Strawberry\perl\bin`) has the modules. Resolved by prepending
   Strawberry Perl to `PATH` for the build.

Defect 3 is environment-scoped, not repository-scoped: it must be applied
whenever the OpenSSL vendored build is invoked from this machine. It is
recorded here as executed-evidence, not as a repo change.

### Structural defects found in PR #103 (why it must not be merged as-is)

1. **Two conflicting migration conventions.** PR #103 adds migrations to the
   ordered `migrations.rs` list *and* leaves loose SQL files split across
   `src-tauri/src/db/` (`043_*.sql`, `046_*.sql`, `049_*.sql`) and a new
   `src-tauri/src/db/sql/` (`0044`–`0052`, plus `schedule-plans.sql`), with
   inconsistent zero-padding. Main's established convention is a single inline
   `M::up(...)` list in `migrations.rs` — **there is no `db/sql/` directory on
   main.**
2. **Runtime `execute_batch` re-applies migration-owned SQL.**
   `attachments.rs:274` and `school_resources.rs:259` call
   `execute_batch(include_str!("db/sql/0044_attachments.sql"))` at runtime, and
   the same SQL is *also* an ordered migration at `migrations.rs:2015`. The
   embedded SQL uses bare `CREATE TABLE` (no `IF NOT EXISTS`), so on a
   database that already ran the migration the runtime path would **error**.
   This is a real double-application hazard, not a style issue.
3. **Draft state with no verified baseline.** PR #103 is draft, and its
   handoff (`HANDOFF.md` on that branch) records interrupted/in-flight work.
   Its claims must not be copied forward as current truth.

### What is genuinely reusable (architecture verified against current main)

The layering and authorization patterns **were verified correct** on this
source:

- **Layering holds.** New UI screens import `*ApplicationService` types from
  `../application/*` and domain types from `../domain/*`; they do not reach
  into `infrastructure/` or `@tauri-apps/*`. E.g. `SchedulePlannerScreen.tsx`
  imports only `schedule-plan-service`, domain types, and shared UI
  components. This matches `.claude/rules/architecture.md`.
- **Tenant scope is derived server-side.** New commands use
  `sessions.require_active_school_scope(&conn)` and
  `auth::authorize_capability_with_actor(...)`; `school_id` is not a
  client-supplied parameter. Verified in `commands/schedule_plan.rs`,
  `commands/school_planning.rs`, `commands/score_import.rs`,
  `commands/review_workflow.rs`. This matches `docs/adr/0004-*` and the
  "UI filtering is not authorization" invariant.
- **Application services validate input** before hitting the repository port
  (e.g. `school-planning-service.ts` throws `ValidationError` for missing
  affected area / source / effective date / coordinator).
- **`db/mod.rs` hardening is real security work**: fails closed when an
  existing database's encryption key is missing, and rejects a recovery
  directory that redirects startup through a replacement symlink.
